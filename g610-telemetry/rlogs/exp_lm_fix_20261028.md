# Experimento: correcao do servico `lm:` (log manager)

## Data: 28/10/2026

## O que mudou

### 1. `vendor/eden/core/hle/service/lm/lm.cpp` — registro da porta com dois pontos

O serviço `lm:` estava registrado como `"lm"` (sem dois pontos). `ConnectToNamedPort` faz
`strncmp` exato no nome, entao `"lm:"` != `"lm"`. A porta `sm:` ja usava `"sm:"` com dois pontos.

Alteracao:
```diff
-    explicit LM(Core::System& system_) : ServiceFramework{system_, "lm"} {
+    explicit LM(Core::System& system_) : ServiceFramework{system_, "lm:"} {
...
-    server_manager->RegisterNamedService("lm", std::make_shared<LM>(system));
+    server_manager->RegisterNamedService("lm:", std::make_shared<LM>(system));
```

Resultado: `ConnectToNamedPort("lm:")` agora tem sucesso (svc #0x1f retorna 0).

### 2. `tests/boot_trace.cpp` — observer nao usa mais printf/snprintf no handler de sinal

`std::printf` / `std::snprintf` chamam `_nl_lookup` (locale) que nao e async-signal-safe e
crasha dentro do handler (`__printf_buffer → _nl_lookup` no `_IO_printf`). Substituido por
`snprintf` + `::write` em todos os blocos do Break (0x26) no observer. Adicionado `return;`
no inicio do tratamento de `number == 0x26` no observer (o diagnostico detalhado agora e
feito por `svc_break` em `svc_dispatcher.cpp`, que ja usava apenas `::write`).

### 3. `src/svc_dispatcher.cpp` — `svc_break` com diagnostico write-only

Adicionado dump dos registos (x0-x7, pc, x30), cadeia de fp (x29), buffer IPC em 0x88000000,
objeto do assert ([0x84434EE8] → obj → vtable), e scan ASCII da stack do guest. Tudo com
`::write` e `read_guest`, seguro em handler de sinal.

## O que funcionou

- **Zero ArbitrateLock** (o ThreadDoVsync band-aid esta gatado por `natural_boot()`)
- **ConnectToNamedPort("lm:") com sucesso** (svc #0x1f, handle 0x101fe)
- **sm::Initialize com sucesso** (svc #0x21 SendSyncRequest handle 0x101fe)
- **SignalProcessWideKey x0=0x8437e20c x1=0xffffffff** x2 (Leave do proprio SDK)
- **Break diagnostico completo** (svc_break imprime fp chain, vtable, objeto, IPC, stack)
- **rc=0** (processo do host sai limpo, nao trava mais no `b self` do Abort)
- Observer consegue rodar sem crashar (sem `IA_NOOB=1` necessario)

## Parede atual: `vt[4]` retorna nao-zero → Abort

Apos `ConnectToNamedPort` e `sm::Initialize`, o SDK chama `vt[4]` (funcao local via PLT,
**nao e IPC — nao ha `SendSyncRequest` para a porta `lm:` no trace**):

```
83aec720: stp x29, x30, [sp, #-16]!
83aec728: add x0, x0, #0x8       ; x0 = &obj[8] (contem handle 0x101fe)
83aec72c: mov w2, wzr            ; w2 = 0
83aec730: bl 0x83ca6270          ; PLT thunk → GOT[0x843935A0] → 0x83C9C660 →
                                  ; GOT[0x8438e7A8] → simbolo resolvido por lazy binding
83aec734: and x0, x0, #0xffffffff
83aec73c: ret
83aec244: cbnz w0, 0x83aec278    ; se nao-zero → Abort → Break → b self → loop infinito
```

O objeto:
- `obj[0] = 0x84370148` (vtable ptr)
- `obj[1] = 0x101fe00000001` (handle 0x101fe nos bits altos, 1 nos bits baixos)
- `vt[3] = 0x827fe740` (override do subsdk0)
- `vt[4] = 0x83aec720` (funcao que falha)

O PLT encadeia por GOT entries que no arquivo apontam para stubs de lazy binding
(circular no ficheiro: `GOT[0x8438e7A8] → 0x83C9C660 → GOT[0x8438e7A8]`). Em tempo de
execucao o lazy binding deveria resolver o simbolo, mas pode falhar se o simbolo nao
estiver em nenhum modulo carregado.
